# Architecture

## Overview

AI Effect & Risk Agent построен как простой serverless-MVP на базе Google Workspace.

### Схема работы

Google Form  
↓  
Google Sheets  
↓  
onFormSubmit trigger  
↓  
Google Apps Script  
↓  
Расчёт эффективности + Gemini API  
↓  
Расчёт R и Rmax  
↓  
Матрица «эффект–риск»  
↓  
Email-отчёт пользователю

## Components

### Google Forms

Используется как пользовательский интерфейс для сбора данных о бизнес-процессе.

Пользователь указывает:

- описание и цель процесса;
- исходные данные и ожидаемый результат;
- показатели процесса без ИИ;
- показатели процесса с ИИ;
- условия применения ИИ;
- информацию для анализа рисков.

### Google Sheets

Используется для хранения исходных данных и результатов.

Основные листы:

- `Ответы на форму (1)` — исходные ответы пользователя;
- `Результаты` — показатели эффективности, IE, Rmax и итоговое решение;
- `Риски` — подробный risk register.

### Google Apps Script

Выполняет основную бизнес-логику.

После отправки формы система:

1. получает новый ответ;
2. извлекает данные из формы;
3. рассчитывает изменения показателей;
4. рассчитывает качество Q;
5. рассчитывает индекс эффективности IE;
6. формирует контекст для анализа рисков;
7. вызывает Gemini API;
8. получает структурированный список рисков;
9. рассчитывает R = P × V;
10. определяет Rmax;
11. применяет матрицу «эффект–риск»;
12. формирует итоговое решение;
13. записывает результат в Google Sheets;
14. отправляет пользователю email-отчёт.

## Gemini API

Gemini используется только для качественного анализа рисков.

Модель:

- выявляет наиболее существенные риски;
- классифицирует их;
- определяет вероятность P;
- определяет влияние V;
- описывает причину и возможные последствия;
- предлагает меры управления.

Gemini не рассчитывает:

- процентные изменения;
- IE;
- R;
- Rmax;
- итоговый тип решения.

Эти значения рассчитываются программно в Google Apps Script.

## Risk categories

Используются четыре категории:

- `LEG` — юридические и репутационные риски;
- `ORG` — организационные и кадровые риски;
- `QLT` — качество результата и ошибки модели;
- `BIZ` — иные существенные бизнес-риски.

## Efficiency calculation

Система сравнивает процесс в двух состояниях:

- без ИИ;
- с ИИ.

Используются показатели:

- `T` — активное время;
- `L` — трудоёмкость;
- `C` — оценочная стоимость;
- `I` — существенные итерации;
- `D` — соблюдение срока;
- `Q` — качество;
- `W` — субъективная нагрузка.

Для T, L, C и I рассчитывается относительное изменение:

`ΔX = (X0 - X1) / X0 × 100%`

## Efficiency Index

Индекс эффективности рассчитывается по формуле:

`IE = (ST + SL + SC + SI + SQ) / 20`

Интерпретация:

- `0.80–1.00` — высокий эффект;
- `0.60–0.79` — заметный эффект;
- `0.40–0.59` — умеренный эффект;
- `< 0.40` — слабый или противоречивый эффект.

## Risk calculation

Для каждого риска используются:

- `P` — вероятность от 1 до 5;
- `V` — влияние от 1 до 5.

Балл риска рассчитывается кодом:

`R = P × V`

Уровни:

- `1–4` — низкий;
- `5–9` — умеренный;
- `10–16` — значимый;
- `17–25` — высокий.

Для процесса определяется:

`Rmax = максимальный R среди выявленных рисков`

## Effect–Risk Matrix

На основании уровня эффекта и риска система формирует одно из четырёх решений:

- **Type 1** — масштабировать как устойчивый сценарий с базовым контролем;
- **Type 2** — масштабировать только с регламентом и мерами контроля;
- **Type 3** — доработать сценарий применения;
- **Type 4** — не масштабировать в текущем виде.

## Hallucination control

В prompt анализа рисков добавлены ограничения, запрещающие модели придумывать обстоятельства, которых нет во входных данных.

Gemini не должен без основания утверждать наличие:

- персональных данных;
- коммерческой тайны;
- NDA;
- договорных ограничений;
- штрафов;
- конфиденциальной информации;
- других специфических условий компании.

Если информация не была указана пользователем, она не должна трактоваться как установленный факт.

## Human-in-the-loop

Форма отдельно собирает информацию о проверке результата человеком.

Human review учитывается при оценке риска:

- обязательная проверка снижает риск;
- выборочная проверка сохраняет риск пропуска ошибок;
- отсутствие проверки повышает риск попадания ошибки в конечный результат.

## Email reporting

После анализа пользователь автоматически получает email-отчёт.

В нём содержатся:

- показатели процесса без ИИ и с ИИ;
- изменения показателей;
- IE;
- уровень эффекта;
- выявленные риски;
- P, V и R;
- меры управления;
- Rmax;
- уровень риска;
- итоговое решение.

Пользователю не требуется доступ к техническим Google Sheets.

## Why this architecture

Для MVP были важны следующие ограничения:

- реализация за короткий срок;
- минимальный бюджет;
- отсутствие отдельного сервера;
- отсутствие DevOps;
- простой пользовательский интерфейс;
- понятная и проверяемая бизнес-логика.

Поэтому Google Workspace используется как serverless-инфраструктура первой версии продукта.
